## 1. 排期结论

建议采用 **7 周、双开发轨并行**，第 6 周产出可提交 RC，第 7 周保留给稳定性结论、发布修正和正式提交：

- A 轨：macOS 平台、UI、权限、显示器、发布。
- B 轨：领域模型、SQLite、同步引擎、Connector、导出与告警。
- QA/产品从第 1 周开始参与真机、口径、接口凭据和验收，不在最后一周集中介入。

7 周基线的资源假设为 **4 名全职工程师**（A/B 轨各 2 名，至少 2 名熟悉 macOS/Swift）、1 名 QA，产品/设计按需参与，并预留约 15% 工程容量处理接口差异和 RC 缺陷。若只有 2 名工程师 + 0.5 名 QA，按依赖顺序执行预估 **12–14 周**；单工程师预估 **20–24 周**。Provider 官方能力和可用管理凭据是最大变量，不应把未验证接口当作确定工期。

## 2. 里程碑

| 里程碑 | 时间 | 退出条件 |
|---|---|---|
| M0 技术验证 | 第 1 周前 2–3 天 | M5、沙箱、Codex、Provider 能力矩阵、1280×720 可读性有书面结论 |
| M1 可运行骨架 | 第 1 周末 | 沙箱 App 可在副屏显示四页 Mock UI；数据库/Keychain/CI 骨架可用 |
| M2 纵向闭环 | 第 2 周末 | OpenAI + 天气从网络到缓存到 UI 闭环；离线可读缓存 |
| M3 Connector 完整 | 第 4 周末 | P0 Connector 均有真实或明确降级状态，账户/价格/导出/告警可用 |
| M4 Release Candidate | 第 5 周末 | 功能、性能、权限、安全、重连通过；无 P0/P1 缺陷 |
| M5 App Store 提交 | 第 7 周末 | 签名、素材、隐私、审核模式、72 小时测试和提交完成 |

范围门：任何 Provider 在 M0/M2 证明没有公开、合规、沙箱可用的数据源时，产品需在 1 个工作日内选择“本地估算并明确标识”“只展示可获得能力”或“移出 P0”；禁止用网页抓取补齐。

## 7. 测试节奏与发布门槛

### 每个 PR

- Format lint、Debug/Release build、模块单测、secret scan。
- Connector 变更运行统一契约测试；migration 变更运行全迁移链。
- UI 变更附 1280×720 截图并检查原型差异。

### 每周

- W1 起进行 M5 真机 smoke；W2 起测试断网/恢复；W3 起测试多账户/币种；W4 起跑完整回归。
- 每周更新 Provider 能力矩阵、风险表和剩余估算，不以“代码完成”代替真实接口验收。

### RC 门槛

- P0/P1 缺陷为 0；P2 必须有 owner、影响说明和批准。
- PRD 第 22、23 节全部有测试证据。
- 冷启动、内存、空闲 CPU、页面切换、副屏恢复达到 PRD 指标。
- Release 沙箱包在干净账户完成权限拒绝、手工城市、导出、登录启动测试。
- 数据库迁移、Keychain、导出、日志通过隐私审查。
- 72 小时连续运行无持续内存增长或不可恢复同步故障。

## 9. 任务看板字段

将上述任务录入项目管理工具时统一包含：

- ID、标题、Epic、PRD ID、Owner、Reviewer、估算、依赖、目标周。
- 数据来源：官方/本地聚合/估算/Mock。
- 权限与隐私影响：Keychain、定位、通知、文件、组织凭据。
- 验收条件、测试证据、原型差异截图。
- 状态：`Backlog -> Ready -> In Progress -> In Review -> Verify -> Done`。
- Blocked 必须写明外部依赖、解除条件和下一次检查时间。

并行限制：每名工程师同时最多 1 个 `In Progress` 主任务；紧急缺陷除外。Provider Connector 只有在 fixture、错误映射与契约测试齐全后才能进入 `Verify`。

## 10. 开工顺序

1. 先执行 TD-001～005，完成五个技术验证门和项目基线。
2. 产品在 M0 当日确认 Provider 降级范围，并记录已采用的 macOS 14+ 最低版本决策。
3. A/B 两轨分别从 TD-020 与 TD-010 开始，W2 用 OpenAI + 天气完成首个纵向闭环。
4. W4 结束冻结 P0 功能，W5 以后只接受阻塞发布的功能调整。
5. RC 达到第 7 节门槛后再生成商店包，不以 Debug/Mock 结果代替 Release 沙箱验证。
